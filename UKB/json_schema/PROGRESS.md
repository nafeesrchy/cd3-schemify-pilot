## How to continue

This conversion runs over several sittings — an agent session can hold only so
much at once, so the work is planned in units that each fit one session. Nothing
is lost between sittings: this file is the memory.

To continue at any time: open a fresh agent session in this package's directory
(or its parent, `Harmonization/CD3_Schemify_Pilot/UKB/`) and invoke the skill again. The agent
reads this file and proposes the next unit. You can also ask for anything
directly — a specific category, a change, a question, the final review.

This is UK Biobank: about 4,450 in-scope fields across 53 categories (D025, D042),
roughly 75x the size of the BGS pilot. Expect this package to run for many,
many sittings — depth over coverage; a category taken all the way to
`validated` in one sitting beats several left half-drafted.

## Conventions

- sentinels: only special answers the source defines, written per field (for UK Biobank the negative codes such as -1 "Do not know", -3 "Prefer not to answer"); none is generated, and a blank cell is rejected · D036, D037 (supersedes D003, D016)
- table: one, `uk_biobank`, as the provider's data is one dataset; category titles carry the artifact path ("Assessment centre — Touchscreen questionnaire: Sociodemographics"); no "PARTICIPANT" prefix · D046
- $id base: https://schemas.example.org/cd3-ukb-pilot/ (replace before publishing) · D011
- grain: see header · title separator: — (em dash) · formatting: 2-space, one key per line · D011
- real data: none in repo; stays inside UK Biobank's own TRE · D004
- routing: faithful · D008
- scope: the CD3 researchers' second-review selection (about 4,470 fields; 7,406 under the earlier plan), not the earlier 7,406-field plan. Private fields, fields with no instance-0 value and the "perhaps request later" rows are tracked in VARIABLES.csv, not silently omitted · D025, D027, D028, D033
- property keys: `f{field_id}` (e.g. `f31`), not an invented name — guarantees uniqueness across all categories under one mother, matches the legacy pipeline's own convention · D017
- bounds: no plausibility bound on a continuous field unless the source states one (`field.txt` has no min/max column at all); a measure with source special answers excludes those codes from the plain number branch via `not: {"enum": […]}` · D013
- units: `x-unit` (machine-readable) when `field.txt` states one, not appended to the title · D018
- dates: `value_type=51` fields use pattern `^[0-9]{4}-(0[1-9]|1[0-2])-(0[1-9]|[12][0-9]|3[01])$` (ISO `YYYY-MM-DD`), confirmed by the steward; each date property's `$comment` still notes the format is assumed, since the source never states the delivered format · D015
- assessment-centre fields (`instanced=1`): initial visit (instance 0) only; one plain scalar `f{field_id}` property holding the instance-0 value, no `{instance, value}` list; the repeat and imaging visits are out of scope · D026 (supersedes D019, D022; D023 closed)
- multi-select fields (`value_type=22`, `arrayed=1`): a list of codes, `maxItems` from `array_max` · D021; how the options show on the dictionary page is open · D031
- a truly invariant coded shape (same codes, same meaning everywhere) gets a shared `common/defs.json` entry, e.g. `yes_no` for UK Biobank's plain binary encoding 7 · D024
- a hierarchical encoding where every node is independently selectable (e.g. `f21000` Ethnic background) is flattened into one `oneOf`, not modeled as a tree · D020
- the dictionary page lists no options for an array property (library limit); the description-text workaround of D022 applied to instanced fields and is gone with them (D026); the multi-select display is open · D031
